# HaruLog iOS — 기술 스택

2026년 현재 iOS 생태계에서 가장 주목받는(핫한) Apple 네이티브 최신 스택을 기준으로 선정했습니다.
카메라·영상 처리·온디바이스 AI가 핵심인 앱 특성상 크로스플랫폼(Flutter/RN)보다 네이티브가 명확히 유리합니다.

## 1. 최종 선정 스택 (요약)

| 영역 | 선택 | 비고 |
|---|---|---|
| 언어 | **Swift 6.x** | strict concurrency 활성화 |
| UI | **SwiftUI** + Observation(`@Observable`) | iOS 26 Liquid Glass는 `#available` 분기 |
| 아키텍처 | **MVVM + Repository** (기능별 SPM 모듈화) | 대안: TCA — 아래 비교 참고 |
| 영속성 | **SwiftData** | 추후 CloudKit 동기화 확장 |
| 카메라/영상 | **AVFoundation** (멀티 세그먼트 녹화), **AVKit**(재생), **AVMutableComposition**(합본) | |
| AI (블로그 생성) | **Foundation Models framework** (Apple Intelligence 온디바이스 LLM) | 미지원 기기는 템플릿 폴백 |
| 위치 | **CoreLocation** + `CLGeocoder` 역지오코딩 | 장소명 자동 태깅 |
| 통계 차트 | **Swift Charts** (Me 탭 확장 시) | 선택 |
| 위젯/단축어 | **WidgetKit + App Intents** (스트릭 위젯, 빠른 촬영) | 2차 릴리즈 |
| 테스트 | **Swift Testing**(단위) + XCUITest(플로우) + swift-snapshot-testing(UI) | |
| 도구 | Xcode 26, SwiftLint, SwiftFormat, GitHub Actions(+ Xcode Cloud) | |
| 배포 | TestFlight → App Store, Fastlane 자동화 | |
| 최소 지원 | **iOS 18** (iOS 26 전용 기능은 조건부 적용) | |

## 2. 선정 이유

### Swift 6 + SwiftUI + Observation
- 현재 Apple 플랫폼의 표준이자 가장 활발히 발전 중인 조합. 와이어프레임의 탭/오버레이/상태 기반 UI가 SwiftUI 선언형 모델과 1:1로 맞아떨어짐.
- `@Observable` 매크로(Observation 프레임워크)는 기존 `ObservableObject` 대비 보일러플레이트가 적고 뷰 갱신 범위가 세밀해 성능이 좋음.
- Swift 6 strict concurrency로 카메라 세션·파일 IO·AI 생성 같은 비동기 작업의 데이터 레이스를 컴파일 타임에 차단.

### SwiftData
- Core Data의 후속으로 `@Model` 매크로 기반 선언형 영속성. `@Query`로 SwiftUI와 직결되어 Today/Timeline/Calendar가 자동 갱신됨.
- 추후 CloudKit 미러링으로 기기 간 동기화 확장 용이.

### AVFoundation (카메라·영상)
- 세그먼트 녹화(멈췄다 이어찍기)는 `AVCaptureMovieFileOutput` 다중 클립 → `AVMutableComposition` 병합으로 구현.
- 데일리 블로그 릴 합본, 썸네일 추출(`AVAssetImageGenerator`)까지 동일 프레임워크로 해결.

### Foundation Models framework (온디바이스 AI) — 이 앱의 차별점
- WWDC25 공개된 Apple Intelligence 온디바이스 LLM API. 캡션·무드·장소·시각을 입력으로 **데일리 블로그 본문을 기기 내에서 생성** — 서버 비용 0, 오프라인 동작, 일기 데이터가 기기를 떠나지 않아 프라이버시 강점.
- `@Generable` 가이드 생성으로 구조화된 출력(제목/본문/해시태그) 안전하게 수신.
- Apple Intelligence 미지원 기기 → 템플릿 기반 문장 조합 폴백. (원격 LLM(Claude API 등) 옵션은 2차에서 검토)

### 아키텍처: MVVM + Repository, SPM 멀티 모듈
- 화면 7개 규모에는 경량 MVVM이 적정. `@Observable` ViewModel + Repository(SwiftData/AVFoundation/AI 추상화)로 테스트 가능성 확보.
- 기능별 SPM 모듈(`DesignSystem`, `CoreData(모델)`, `CameraKit`, `BlogAI`, 각 Feature)로 빌드 시간·의존 방향 관리.

#### 대안 비교: TCA (The Composable Architecture)
- 장점: 상태 추적·테스트에 매우 강력, 커뮤니티 활발. 단점: 러닝커브·보일러플레이트, 이 규모에선 과투자.
- **결론**: 1인/소규모 팀 MVP는 MVVM 권장. 팀 확장·상태 복잡도 증가 시 Feature 단위로 TCA 도입 가능한 구조(모듈 경계)만 확보.

### 크로스플랫폼을 배제한 이유
- 핵심 기능 3가지(멀티 세그먼트 카메라, 영상 합성, 온디바이스 AI)가 모두 플랫폼 네이티브 API 의존 → Flutter/RN은 브리지 비용만 늘고 이점이 없음. Android 확장 시점에 Kotlin 네이티브로 별도 개발이 현실적.

## 3. 디자인 시스템 매핑

와이어프레임의 네오브루탈 스타일을 SwiftUI 토큰·수정자로 체계화:

```swift
enum HLColor {           // Asset Catalog 연동
    static let ink = Color("Ink")            // #131826
    static let blue = Color("Blue")          // #0967F5
    static let purple = Color("Purple")      // #A855F7
    static let paper = Color("Paper")        // #F4F5F7
    static let placeholder = Color("Placeholder") // #E9EBF0
    static let muted = Color("Muted")        // #9FA5B2
    static let gray = Color("Gray")          // #4F5663
}

// 하드 섀도우 + 잉크 보더 카드 (재사용 수정자)
struct HardCard: ViewModifier { ... }   // .background(.white) .border(ink, 2) .hardShadow(6)
```

- 폰트: 손글씨 무드 유지 — 한글 지원 폰트(예: 나눔손글씨 계열 임베드) + SF Pro 폴백. 라이선스 확인 후 확정.
